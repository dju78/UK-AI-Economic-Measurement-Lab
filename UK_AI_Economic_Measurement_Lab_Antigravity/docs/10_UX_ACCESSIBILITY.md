# 10 — UX, Content and Accessibility Specification

## 1. Design principle

The product should feel like a serious public analytical service: calm, evidence-led, accessible and transparent. It may learn from ONS/GOV.UK service-design principles but must have its own independent identity. Do not copy the ONS masthead/logo.

## 2. Required global elements

- independent prototype phase banner;
- project name and version;
- data-vintage link;
- methodology link;
- accessibility statement;
- source status legend;
- feedback/contact link.

## 3. Content pattern for analytical pages

1. What this page answers.
2. Key source facts.
3. Interactive analysis.
4. What this means.
5. What this does **not** mean.
6. Method and assumptions.
7. Data/source links.
8. Download/reproduce.

## 4. Accessibility

Target WCAG 2.2 AA as project standard.

- one H1 per page;
- logical heading hierarchy;
- visible keyboard focus;
- all interactive controls operable by keyboard;
- no information conveyed by colour alone;
- chart alt summary and accessible data table;
- form labels and useful error messages;
- 200%/400% zoom resilience;
- responsive layouts;
- reduced-motion preference respected;
- plain English around technical content.

ONS Service Manual emphasises accessible, user-centred services and its Design System includes guidance/components for consistent accessible products. [S11]

## 5. Chart rules

- start axes appropriately; explain exceptions;
- display units and reference periods;
- avoid 3D charts;
- use uncertainty intervals/ribbons where relevant;
- allow data table view;
- show source directly below chart;
- label prototype estimates explicitly.

## 6. High-risk wording

Avoid:
- “true AI value”;
- “the AI share” where it is assumption-based;
- “ONS-style estimate”;
- “official” for project output.

Prefer:
- “illustrative AI share assumption”;
- “experimental scenario”;
- “published broad product total”;
- “indicative decomposition”.
